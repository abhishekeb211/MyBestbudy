# QuestMind 3.0 — Actionable Build & Audit Checklist

**Status:** All tasks start unchecked. No code, UI, test result, owner sign-off or completed trial was supplied.  
**Use with:** [`QuestMind_Project.md`](QuestMind_Project.md) for the design, [`log.md`](log.md) for decisions and corrections.  
**Legend:** **P0** before real-user testing; **P1** core MVP; **P2** after feasibility; **P3** defer unless justified.  
**Definition of done:** a checkbox can be marked `[x]` only after a deliverable **and** review evidence are linked in `log.md`.

## Phase 0 — Scope and rules of the game [P0]

- [ ] **S01** One-sentence pitch approved: practical everyday thinking and habits, not therapy or diagnosis. Evidence: signed product brief. [D-001]
- [ ] **S02** Define intended audience and first research cohort; capture inclusion/accessibility needs. Evidence: research/recruitment brief. [D-013]
- [ ] **S03** State prohibited claims: cure, diagnosis, IQ boost, hidden personality measurement, guaranteed improvement. Evidence: approved copy guide. [D-002]
- [ ] **S04** Keep five modules, with only one main suggested quest daily. Evidence: journey map. [D-003]
- [ ] **S05** Specify 60–90 second *active screen* target and optional longer offline actions. Evidence: timed prototype protocol. [D-003]
- [ ] **S06** Assign owners: product, design/accessibility, engineering, privacy, safety/content, research. Evidence: responsibility matrix.
- [ ] **S07** Locate missing reference screenshots and actual 25-criteria list, or explicitly mark unavailable. Evidence: asset inventory. [D-001]
- [ ] **S08** Create a content claims/evidence register; attach research references and uncertainties. Evidence: documented citations. [D-002]

**Gate 0:** complete S01–S06 and a reviewed initial risk register; unresolved sources are disclosed rather than invented.

## Phase 0 — Safety, accessibility and trust [P0]

- [ ] **T01** Document Help pathway, emergency limitations and verified support resource approach; no false staffed-human promise. [D-014]
- [ ] **T02** Review every initial scenario for harmful assumptions, stigmatizing wording, age suitability and distress triggers. [D-006]
- [ ] **T03** Ban self-harm, trauma, substance misuse and other dangerous reward/challenge mechanics. [D-014]
- [ ] **T04** Remove "collect the no", mandatory psychological timers, streak-loss penalties, and hidden psych scoring. [D-007/D-009/D-010]
- [ ] **T05** Ensure all basic quests have readable-text, screen-reader, reduced-motion, and low-mobility pathways. [D-004]
- [ ] **T06** Define who can reject a release for safety/privacy reasons and how rollback occurs. Evidence: incident and release policy. [D-015]
- [ ] **T07** Create and execute a scripted content-safety test list with expected and actual results; before execution, mark actual results NOT RUN. [D-014]

**Gate 1:** reviewed user-facing content, functioning Help path and no unresolved critical safety/accessibility problem.

## Phase 1 — User experience & educational content [P1]

- [ ] **U01** Wireframe onboarding, Map, Drop, feedback, Move, Pause, Help and Settings.
- [ ] **U02** Show plain-language "what we collect / what we do not infer" during onboarding. [D-011]
- [ ] **U03** Create a usable avatar/map with cumulative progress and no penalties. [D-010]
- [ ] **U04** Write 12–20 short Drop scenarios, each teaching exactly one explicit practical skill. [D-006]
- [ ] **U05** Add a simple explanation and at least one alternative response to each Drop; label uncertainty appropriately.
- [ ] **U06** Ensure emotional experiences are not graded as correct/incorrect; distinguish lesson correctness from personal feelings.
- [ ] **U07** Provide "Useful / Not useful / Skip" reflection; do not derive mental-state labels. [D-008]
- [ ] **U08** Prototype optional Move and Quiet Quest, including cancel/skip. [D-004/D-005]
- [ ] **U09** Provide manual accessible alternatives to step counting and full quest progress without permissions.
- [ ] **U10** Create at least 3 realistic user journeys: busy student, user with restricted movement, user refusing every permission.
- [ ] **U11** Test wording, screen time, reading level and emotional comfort with consented adult users.

**Gate 2:** users can explain the experience, complete and skip tasks without coercion, and finish the small in-app loop within the intended time under tested conditions.

## Phase 2 — Minimal offline implementation [P1]

- [ ] **E01** Choose client platform after feasibility testing; document Android/iOS feature differences.
- [ ] **E02** Implement a local, versioned, reviewed content catalog; no autogenerated unapproved scenarios. [D-012]
- [ ] **E03** Implement deterministic quest selection using user preference, available alternatives and permissions. [D-012]
- [ ] **E04** Make the app work with airplane mode enabled and all optional permissions denied. [D-011]
- [ ] **E05** Store only minimal progress and chosen settings with appropriate on-device protection. [D-011]
- [ ] **E06** Do not embed third-party tracking/advertising SDKs in the initial build. [D-011]
- [ ] **E07** Ensure no location, contacts, microphone, social graph or reaction-time profiling exists in core logic. [D-011]
- [ ] **E08** Clearly distinguish self-reported Quiet Quests from device-verified sessions; do not overclaim measurement. [D-005]
- [ ] **E09** Implement granular optional permissions and revocation without game penalty. [D-011]
- [ ] **E10** Implement erase/reset/export functions, and document how backups and synced copies are handled. [D-011]
- [ ] **E11** Test unauthorized access, local database exposure, logs, crash reports and dependency security. [D-011]
- [ ] **E12** Do not add runtime conversational AI without an incremental-benefit and safety review. [D-012]
- [ ] **E13** Keep all users' personal activity data out of development-agent prompts and external analytics unless specifically justified and consented.
- [ ] **E14** Add automated tests for content approvals, permissions, offline mode, accessibility alternatives, deletion and Help screens.

**Gate 3:** passing functionality, safety and privacy tests, linked to source commit/build and named reviewers. Automated coverage does not replace human review.

## Phase 3 — Feasibility and research [P1]

- [ ] **R01** Draft research question: does the app teach a measurable skill or help voluntary real-life action? [D-002]
- [ ] **R02** Choose one primary outcome and independent **unseen** assessment items, not game replay scores. [D-002]
- [ ] **R03** Distinguish usability, skill learning and real-life transfer in the protocol. [D-002]
- [ ] **R04** Register inclusion criteria, recruitment, consent, data scope, exclusion/withdrawal policy and risk management.
- [ ] **R05** Conduct appropriately reviewed usability sessions before a broader pilot; log real counts, not guesses.
- [ ] **R06** Run a feasibility pilot with a justified sample; report uptake, return, technical problems, pressure and discomfort.
- [ ] **R07** Record how many people decline step/screen-time permissions and whether they can still benefit.
- [ ] **R08** Use a credible active control in any efficacy comparison; estimate uncertainty, harms and attrition.
- [ ] **R09** Compare original feature combination with a simpler version to determine which module adds value. [D-018]
- [ ] **R10** Do not label percentage targets as QuestMind results before collecting data. [D-016]
- [ ] **R11** Record negative or null results with equal prominence to positive findings. [D-016]
- [ ] **R12** Make a documented go/revise/stop decision after each stage and link it to the next release. [D-015]

**Gate 4:** documented feasibility evidence exists before promising effectiveness; independent comparative evidence exists before making broad improvement claims.

## Phase 4 — Optional modules and governance [P2 / P3]

- [ ] **X01 [P2]** Build optional Belief Forge only after reviewed cognitive content proves understandable; avoid therapy claims.
- [ ] **X02 [P2]** Build educational Skill Tree around demonstrated learned tasks, not psychological classifications.
- [ ] **X03 [P2]** Test whether user-controlled content preferences help more than a static default.
- [ ] **X04 [P2]** Add safe, consent-based Connect challenges only after a separate risk review. [D-007]
- [ ] **X05 [P3]** Keep social squads disabled until moderation, reporting, harassment prevention and privacy controls are funded.
- [ ] **X06 [P3]** Assess agentic runtime AI against a rules-based baseline; ship only if value is demonstrated and privacy/safety gates pass. [D-012]
- [ ] **X07 [P3]** Consider cross-device sync only when user value justifies encryption, account and deletion complexity.
- [ ] **X08 [P3]** Review any younger-user version with its own appropriate content, privacy, safety and evaluation plan. [D-013]
- [ ] **X09 [P3]** Keep governance off-chain by default; no tokens tied to personal disclosures or perceived distress. [D-017]
- [ ] **X10 [P3]** For institutional partners, forbid individual-level psychological performance reports and unsafe peer comparisons.

## Continuous audit checklist — every iteration

- [ ] **A01** Has a `D-xxx` decision been added or updated in `log.md` for each material design change?
- [ ] **A02** Does the entry separate **source evidence**, **assumption**, **proposed test**, and **actual observed result**?
- [ ] **A03** Is the previous decision preserved when superseded rather than silently overwritten?
- [ ] **A04** Has someone tried to falsify the improvement claim with a simpler baseline and alternative explanation?
- [ ] **A05** Were privacy permissions, data retention, accessibility, safety, and measurement checked after the change?
- [ ] **A06** Can the feature be disabled or rolled back without losing essential user functionality?
- [ ] **A07** Is a real owner and reviewer named, with date, evidence path and disposition?
- [ ] **A08** Have any unresolved safety/privacy blockers stopped the relevant release?
